# Harta 下一轮增长升级建议

2026 年 11 月 26 日，基于本地版本 `afd7671`、项目验收记录、合成数据复现及上游 GitHub 仓库。

下一轮建议同时缩短两段时间，从一批评论里找到首个值得跟进的客户，以及从业务资料做出首篇愿意发布的作品。先校准线索统计，再对照不同找客与创作方法，最后用真实发布窗口验证成效。Harta 已经有双路径工作台、带原话的线索分级、制作稿逐处改写与撤回、发布登记及效果导入，可以直接在这些入口上升级。[产品目标](../GOAL.md) · [线索分级](LEAD-QUALIFICATION.md) · [制作与改稿验收](CREATIVE-REVISION-ACCEPTANCE-2026-11-21.md)

## 本轮实现与使用

| 用户要做什么 | 工作台入口和结果 |
| --- | --- |
| 找到值得联系的人 | 「主动截流」继续按原话核实。「客户跟进」中设业务有效条件，总览分别显示符合条件和有实际联系记录的人数。「批量采集」的已完成批次可核对目标准确度、首条核实耗时和请求用量。历史缺失与零结果分别显示。 |
| 用自家资料创作获客内容 | 在「内容创作」选择目标与平台。研究和选题围绕读者会问的问题，制作和审稿按题查找业务原文，保留型号、适用条件和例外。图文给出读者可以照做的判断，短视频用可拍的动作展示判断过程。「检查与交付」可展开依据及版本。 |
| 完成中断的内容任务 | 任务中心可从已保存阶段继续；上次供应商请求是否已计费尚不确定时，可选择是否重发。完成的任务有阶段用量和耗时，旧业务缺失的用量显示为未知。 |
| 确认作品带来的经营结果 | 「账号复盘」优先显示作品及目标结果，可按发布目标和窗口筛选。官方作品读取保留历次累计观测。店铺流水先预览，重复订单和退款可重放，作品归属更正需确认。对账窗口的数据变化会使相关复盘记忆暂停，重新核对后才能用于创作。 |

以「厨房收纳盒卡住柜门」的合成业务为例。同一份素材、同一个模型替身，原稿以“欢迎私信咨询”收尾。新版先让读者慢慢合门，区分盒盖碰门和盒身顶住铰链，再问“如果柜门还会卡住，私信说一下，是盒盖碰到门边，还是盒身顶到铰链？”这句话出现在小红书图文的可发布正文和抖音短视频的口播末句。只有业务确认本平台的联系方式时才用对应入口，其他情况优先给读者一个自查动作。

两条路径沿用现有授权来源，用户在平台发布和联系。本轮使用合成业务、隔离账号和本地模型替身。实际咨询变化、订单结果和经营者用时仍需真实发布数据与反馈验证。[批次核实](LEAD-QUALIFICATION.md) · [创作对照与可选盲评](../evals/creation/README.md)

**隔离验收结果**

- 在培训、家装和电商资料的开头、中间、末尾分别放置依据，9 组均找到了原句及适用例外，并在成稿新增承诺时定位到相应依据。另用仅适用于红款的承重说明重测，蓝款沿用旧选题时被拦下。
- 同一研究隔一分钟运行两次，合计模型调用从 4 次降到 2 次，搜索从 2 次降到 1 次。另一组模拟两篇来源中一篇正文暂时不可读，第二次只补读这一页。
- 在事实核对阶段强制中断本地进程，手机端重新打开后可从上次进度继续。取消重发产生零次额外调用，确认后只重试核对。中途更改业务承接范围时，旧任务停止恢复。

**对抗式业务复验**

- 分两次采入同一批评论，第二篇的评论也进入最终抽样。把同一平台身份放进两份历史联系人档案，任一档案记录停联后，已有待发草稿随之取消。
- 只对小红书开放私信，抖音成稿改用文中可执行的自查动作。已过期的活动价格会在制作稿交付时触发重新核对。模拟模型成功返回不合格稿件和审读结果，继续任务可复用已完成的选题和通过的成稿。
- 导入同店同退款号对应两笔订单、同笔支付对应两篇作品的文件，整批退回核对。更正发布时间时按店铺时区保护已归属订单。待归属流水增加后，重新确认窗口也会保留旧创作记忆的失效状态。

## 1. 先修经营看板，再优化找客顺序

**已复现。** 同一个合成联系人，没有新增客户原话或资格评定，只把阶段从“待核实”改为“已联系”，首页采用的已核实人数就从 0 变为 1，两次的正式分级都是“待核实”。在无独立购买需求的联系人上，人工登记已发送就能触发这次阶段变化。按这个总数计算获客成本，会奖励多做联系动作的批次。[看板](../js/studio-overview.js#L29) · [统计规则](../js/business-results.js#L23) · [发送登记](../lib/acquisition-workspace.mjs#L614)

**第一步。** 首页分别取有实际联系记录的人数、满足本业务有效条件的人数。后一项关联原话、适配条件、核实时间和当时的规则版本。沿用同平台稳定身份的去重和两路交集，允许同一人有多个购买需求。业务自行约定哪些条件算有效，例如培训机构可要求课程适配且家长确认试听，不能统一把所有 B 级算进去。旧记录保留原阶段，缺依据的列为待核实。

**第二步。** 对每次搜索保留搜索词、作品、评论、筛选理由和人工结论，连接现有批次请求账本。把新旧排序的前十条混排，隐藏原排名供经营者核实，再从双方都排除的评论中随机抽查。对照前十命中数、找到首条有效需求的分钟数、每位新增有效联系人的 API 请求数和人工分钟。结果为零的批次单列总投入与排除原因。小样本时，低位抽查只报告抽样结果。[现有分歧队列](../vendor/openfind/server/qualification-comparison.ts#L18) · [流程请求账本](../lib/request-budget-core.mjs#L21)

**GitHub 取舍。** `ir_measures` 可以离线读取人工判断与排序，输出前十命中比例和前十已评比例。用匿名编号即可与 Node 服务分开运行。首轮样本很少时，Harta 自己也可以算这两个数。接入成本低，主要投入是经营者标注时间。[terrierteam/ir_measures · Apache-2.0](https://github.com/terrierteam/ir_measures#command-line-interface)

## 2. 让创作和事实核对找到同一条原文

**已复现。** 已读取的附件合计超过 3 万字符时，系统给每份资料分配预算，对超长部分取前 70% 和后 30%。我把唯一一句规格说明放在一份约 3.8 万字资料中间，函数给出了取样警告，那条规格没有进入上下文。写作与事实核对都可能面对同一个缺口。销售侧已经能按业务、产品、规格和有效期限定范围，并返回原文、版本和位置。[创作资料取样](../lib/content-context.mjs#L8) · [事实核对输入](../lib/content-review.mjs#L20) · [销售资料检索](../lib/sales-knowledge.mjs#L4)

**升级建议。** 用本篇读者问题、具体产品和待核实的承诺，从可用资料里找相关段落。把适用范围、例外和冲突版本一起送审，保留文档版本与原句位置。核对阶段再针对成稿里的数字、报价与交付承诺查一次。没有依据时沿用现有补资料或删句操作。用户仍从“创建内容”进入。

**验收。** 用本地培训的服务半径、家装的安装例外、电商近似型号的尺寸构造对照。把正确原句放在开头、中间、末尾，混入过期报价和另一型号的相似句。在相同输入预算下比前五段能否找到依据、错用条件次数、经营者改稿分钟。先复用已有中文双字检索。若漏检集中在用词和排序，再试可自定义分词和字段权重的 MiniSearch。它可在当前 Node 进程运行，接入成本主要是索引版本与中文样本验证。[lucaong/minisearch · MIT](https://github.com/lucaong/minisearch#tokenization)

## 3. 降低一篇可采用成稿的等待与调用成本

研究有 24 小时缓存，但任一警告都会关闭整份研究结果的缓存资格。“未配置可选 5118”本身就会产生警告。隔离复现里，同一输入间隔一分钟执行两次，用替身记录到 4 次模型调用和 2 次搜索调用。另一个可见问题是内容任务中断后，用户需要点“重出”。生成层已有研究完成回调，可从这一处保存中间结果。[缓存读取与数据源状态](../lib/research.mjs#L159) · [缓存写入条件](../lib/research.mjs#L220) · [研究完成回调](../lib/generate.mjs#L1306) · [中断后的行为](../lib/workspace.mjs#L288)

**先交付缓存小改动。** 记录未配置、执行成功和临时失败三种状态。用户继续看到缺少 5118 的提示，配置稳定时可复用成功的搜索和研究。上面的相同夹具以两次运行合计 2 次模型调用、1 次搜索为验收目标。资料、数据源、模型或任务依据变化时须重新验证。

**再做分段恢复。** 用现有 SQLite 先保存研究结果，再扩到选题、成稿与核对。恢复前比对业务、输入版本和阶段。对已发请求、响应是否落盘仍未知的情况单列，防止静默重试导致重复费用。补记模型返回的 token 用量、耗时与失败阶段，在同质量的成稿之间比较每篇实际用量和等待时间。供应商账单、费用估算、保护预留分别记录。[当前模型响应](../lib/llm.mjs#L510) · [预算预留](../lib/model-spend.mjs#L53)

**GitHub 取舍。** DBOS 给出了从最后完成步骤恢复的实现，其 TypeScript SDK 需要 PostgreSQL。本轮借鉴检查点和重放设计，改动集中在 Harta 的内容任务模块。跨实例调度成为明确需求时再评估直接接入。[dbos-inc/dbos-transact-ts · MIT](https://github.com/dbos-inc/dbos-transact-ts)

## 4. 按当初选的目标复盘发布结果

**已复现。** 给同账号、同平台、同窗口的两篇作品分别提供指标。在当前账号复盘对照函数中，仅填阅读量时生成 1 个对照组，仅填分享数或仅填有口径的订单数时都是 0 组。Harta 已能登记这些指标，缺口发生在比较环节。抖音官方作品列表的读取路径也已实现，对同一已发布作品再同步会更新最近一次官方快照。项目记录中，这条官方授权路径完成的是模拟响应验收。[复盘分组](../js/creator-review.js#L26) · [已支持的指标](../js/growth.js#L4) · [官方快照更新](../lib/platform-auth.mjs#L184) · [授权验收范围](FUNCTION-PRESERVATION.md#L215)

**先用已有数据做全四种目标。** 流量看可取得的阅读或播放，结合受众相关证据。传播看分享与同账号基线。获客看按同一业务条件核实的去重联系人。成交先看有订单依据的成交数与退款。每组显示作品版本、账号、来源和窗口。区分自然与付费需要有实际来源依据。只有总曝光时，将人群相关性留作待核实。

**再验证一个真实来源。** 先用授权商家已有的平台导出表，沿用现有 CSV 预览。如果试点商家有抖音作品权限，再将同一作品的不同观测时点追加保存，显示实际观测日期及累计值。相同观测重放一次，结果应相同；两次累计值不相加。电商业务下一步可从一份订单与退款导出开始，以店铺、订单 ID、退款 ID 对账，作品来源不明确的留作待确认。[现有效果导入](../lib/account-review.mjs#L53)

**GitHub 取舍。** Singer 的 RECORD、主键与 STATE 规范适合参考，用来区分收到的记录、观测时间和成功保存后的同步位置。Harta 可以沿用现有 Node 导入器。接入成本取决于拿到真实样表或只读授权。[singer-io/getting-started · 同步规范](https://github.com/singer-io/getting-started/blob/master/docs/SPEC.md)

## 试点与投入顺序

| 顺序 | 交付 | 判断是否继续投入 |
| --- | --- | --- |
| 第一批 | 修正“已核实”计数。并行修研究缓存，记录找客、改稿、调用与等待的初始值。 | 联系动作不能提高核实人数。相同研究输入的重复调用按夹具预期下降，资料变化后仍能重查。 |
| 第二批 | 选本地培训、家装服务、电商各一个获授权业务，用同批评论和同套业务资料对照前十候选及新旧稿件。 | 经营者盲核候选、盲选稿件并实际改一稿。图文实际排一组，视频实际拍第一镜。检查前十命中、人工分钟、错用承诺、可用稿的模型用量。达到同等或更高质量且少耗时，再扩大。 |
| 第三批 | 把实际采用的作品按账号登记发布，在预先约定的时间窗回看一个主要结果。 | 可比作品分别对照阅读、分享、有效客资或有凭据的订单。保留未知与零值的差异；样本不足时扩大观察，不据此推算因果收益。 |

Harta 已用 Promptfoo 跑 13 个合成销售场景，现有真实模型创作矩阵覆盖一套厨房资料、两种目标。可复用当前版本和自定义 provider，为传播、成交及长资料检索增加测试。历史一次 16 组真实模型运行有 14 组出稿、13 组完成事实辅助核对、10 组完成内容诊断。以上数字是该次运行记录；经营者实际改稿时间和发布后咨询量仍需通过试点采集。Promptfoo 适合比较版本与记录失败样例，采用决定与经营结果由试点提供。[Harta 销售评测](../evals/sales/README.md) · [创作矩阵](../scripts/check-content-matrix-live.mjs#L16) · [历史验收](PRODUCT-OUTPUT-REVIEW-2026-11-20.md#L98) · [promptfoo/promptfoo · MIT](https://github.com/promptfoo/promptfoo)
